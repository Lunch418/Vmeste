# SECURITY_REVIEW.md — «Вместе», полный проход по backend

Полный (не точечный) проход по всему `backend/app/` — в отличие от
`specs/REVIEW.md`, который разбирал только код-ревью MVP в целом, и от
security-подраздела `specs/CHANGES.md`, который касался только новой
фичи взаимного check-in. Дата: 2026-08-06.

## Вердикт: 🔄 Changes Requested → исправлено в этом же проходе

Найдены 1 Critical, 2 Major, 3 Minor. Critical и оба Major исправлены
сразу; Minor #4 (JWT в localStorage) и #7 (устаревшая `python-jose`) —
задокументированы как принятые компромиссы/задачи на будущее, не

## Critical — исправлено

### 1. Webhook без аутентификации мог откатить расчитанный депозит обратно в `held`
`backend/app/routers/deposits.py` (было: строка 60)

`POST /deposits/{id}/webhook` не имеет проверки подписи провайдера (это
осознанная заглушка — ЮKassa не подключена, см. `specs/CHANGES.md`). Но
до исправления обработчик безусловно ставил `escrow_status = held`
независимо от текущего статуса. `deposit_id` — обычный UUID без
дополнительного секрета, виден авторизованным пользователям через
`DepositOut`. Сценарий: депозит уже расчитан (`refunded` после
`/refund`, `released_to_poster` после неявки, `forfeited` после
компенсации) → кто угодно (эндпоинт не требует авторизации, т.к.
реальные вебхуки шлёт сам провайдер, не пользователь) вызывает
`webhook` → статус снова `held` → плательщик повторно вызывает
`/refund` → двойной возврат.

**Исправлено**: вебхук теперь no-op, если депозит уже не в `held`.

## Major — исправлено

### 2. Нет rate-limit на запрос/проверку SMS-кода — полный account takeover
`backend/app/sms.py`, `backend/app/routers/auth.py`

- `POST /auth/phone` не имел ограничений — можно было бесконечно
  запрашивать код на чужой номер.
- `POST /auth/verify` не имел счётчика неудачных попыток. Код — 4 цифры
  (10 000 вариантов), TTL 5 минут, без rate-limit — реалистичный брутфорс
  за отведённое время. Успешный подбор = вход в чужой аккаунт (или
  создание нового, если аккаунта не было) — полный account takeover
  любого номера телефона.

**Исправлено**: `app/sms.py` — cooldown 30 сек между запросами кода,
лимит 5 запросов/час на номер, лимит 5 попыток ввода кода на один
сгенерированный код (после — код инвалидируется). `/auth/phone`
возвращает 429 при превышении лимита.

### 3. CORS: `allow_origins=["*"]` вместе с `allow_credentials=True`
`backend/app/main.py`

При такой комбинации Starlette не отправляет буквальный `*`, а
отражает `Origin` запроса — фактически «credentialed-запросы разрешены
с любого источника». Сейчас ущерб ограничен тем, что JWT лежит в
`localStorage` и добавляется вручную в заголовок (не автоматическая
cookie), но при любом будущем переходе на cookie-сессии эта
конфигурация станет тривиально эксплуатируемой межсайтово.

**Исправлено**: явный allow-list через новую настройку
`CORS_ALLOWED_ORIGINS` (по умолчанию — только `localhost:5173`).

## Minor

### 4. JWT в `localStorage`, срок жизни 30 дней, нет отзыва на сервере
Разумно для MVP; `logout()` чистит только клиентское состояние — токен
остаётся валиден до истечения. Задокументировано, не блокирует MVP.

### 5. Дефолтный `jwt_secret` без предупреждения при старте — исправлено
Уже отмечалось в `specs/REVIEW.md` (Major #4). **Исправлено**: при
старте с дефолтным секретом в лог пишется явное предупреждение
(`backend/app/main.py`, `lifespan`).

### 6. Свободнотекстовые поля без ограничения длины — исправлено
`MessageCreate.text`, `EventCreate.description`/`location_address`/
`activity_type`, `SelfieConfirm.filter_name`, `ReportCreate.reason` и
другие не имели `max_length` — дешёвый вектор storage/bandwidth DoS.
**Исправлено**: добавлены разумные ограничения длины по всем текстовым
полям в `backend/app/schemas.py`, включая WS-путь чата
(`backend/app/routers/chat.py`), который идёт в обход Pydantic.

### 7. `python-jose` — устаревшая, слабо поддерживаемая библиотека
Текущее использование безопасно (алгоритм жёстко зафиксирован как
HS256 при `encode`/`decode`, классическая atack «alg confusion» не
применима), но стоит в будущем перейти на `PyJWT`. Не блокирует MVP.

## Подтверждено безопасным (без замечаний)

- **SQL-инъекции**: везде ORM-запросы с параметризацией, ни одного
  raw SQL/строковой подстановки не найдено.
- **IDOR**: пройдены все `{id}`-эндпоинты в `users.py`, `events.py`,
  `deposits.py`, `confirm.py`, `chat.py`, `notifications.py` — владение
  проверяется везде, где должно.
- **WebSocket-чат**: проверка токена, существования пользователя,
  бана и реального участия в событии — до `accept()`; нельзя
  подключиться к чужой комнате.
- **XSS**: `dangerouslySetInnerHTML`/`innerHTML` не используются нигде
  во фронтенде — React экранирует по умолчанию.
- Зависимости (`requirements.txt`, `package.json`) — без явно
  устаревших/CVE-версий, кроме уже отмеченной `python-jose`.
